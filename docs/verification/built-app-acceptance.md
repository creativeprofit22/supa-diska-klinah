## Picker open from the UI: RESOLVED, verified by operator click

During the run the operator reported that the picker did not open, which was
investigated and is now **resolved as not reproducible**. The report arose while
no app instance was running: both instances are closed by `CloseMainWindow` in
the script's `finally` blocks (lines 535-542, 568-575), so at the time of the
report there was no application in which a dialog could appear.

A fresh instance of the same binary was launched detached (PID 8024,
`Responding=True`, window title "Supa Diska Klinah", nonzero `MainWindowHandle`
— the owner HWND the native dialog requires). Inspecting the mounted page over
the WebView debug socket showed `/#/large-files` with an **enabled** "Choose
folder" button and **no `role=alert` message** anywhere on the page. The
operator then clicked that button in the running app and confirmed the Windows
folder-picking window appeared.

Scope of that confirmation, stated precisely:

- **Verified:** the user-facing path — a real click on the real "Choose folder"
  button in the built app — opens the native dialog.
- **Verified separately, over IPC:** cancel followed by a further successful
  open (`pickerCancel` → `pickerChoose`), plus six opens within one session, so
  reopen after cancellation works at the command level.
- **Not separately exercised:** a click-cancel-click sequence driven entirely
  through the button. The UI open and the IPC reopen are each confirmed; the
  combined UI reopen is inferred, not measured.

The remaining caveat on the rows above stands: every picker open *inside the
automated run* went through `invoke('choose_storage_root')` directly
(`scripts/acceptance-storage-builtapp.ps1` lines 215, 228, 245, 386, 453, 474),
so the harness evidence covers the native dialog and its command, and the
operator click above covers the button that reaches them.

### Open path traced

- **Capability is not the blocker.** `allow-choose-storage-root` is present in
  `src-tauri/capabilities/main.json`. No Tauri dialog plugin is involved: the
  picker is a custom COM `IFileOpenDialog` in `storage/root_picker.rs`, so no
  plugin permission gates it.
- **The native guard cannot stick.** `ScopeService::choose` takes `picker_open`
  by compare-exchange and returns `JobError::Busy` if a dialog is already up,
  but the flag is released by an RAII `Permit` on every return path including
  errors and unwinds. A permanently "busy" picker is therefore not the cause.
- **Native failures are real errors, not silence.** `owner == 0` or a failing
  `window.hwnd()` produce `InvalidRequest` / `unavailable`; a COM failure maps
  to `folder_picker_unavailable`. All surface to the renderer.
- **The remaining silent-no-op shapes are in the frontend**, and none were
  triggered here. In `useStorageRoot.acquire`,
  `if (!mounted.current || locked.current) return;` exits with no dialog, no
  error and no state change; the button is `disabled={root.picking || active}`,
  so it is inert while a scan runs or a pick is in flight; and the `finally`
  clears `locked`/`picking` only when `version === generation.current`, so a
  generation bump mid-pick would leave the button stuck disabled reading
  "Choosing folder…". Observed state before the confirming click was the
  opposite — button enabled, no alert — so these paths remain theoretical and
  unexercised rather than implicated.
- **Single-use authorization is unrelated to opening.** It gates *scanning* with
  an already-chosen root; it does not suppress the dialog.

## Open items

1. **Execution-time identity guard unproven.** A plan built from a selection
   whose on-disk identity changed after the snapshot was still *created*
   (`staleSelection.refused` false). The guard exists at the mutation layer
   (`cleanup/filesystem.rs:45`, `:356` — "identity guard rejected"), so creation
   is plausibly the wrong checkpoint to assert, but this run never executed such
   a plan and no fixture covers the execution-time refusal. Unverified.
2. **Repeat undo is accepted, not refused.** Undoing an already-undone execution
   returned the same completed summary rather than refusing
   (`undoReplayRefusal.refused` false). Idempotent replay is a defensible
   design; it is recorded as observed behaviour, not endorsed.
3. **Misleading refusal code.** The whole-group duplicate plan was correctly
   refused, but reported `snapshot_unavailable` while the very same snapshot
   immediately served a partial plan. The safety outcome is right; the code is
   inaccurate.
4. **`resourceObservation` step failed** with `invalid_evidence` (harness used a
   released snapshot). Harness defect, not app behaviour; the resource figures
   above come from the steps that did complete.

### Follow-up (22 September 2026)

- Item 1: `cleanup::execution::tests::storage_execution_refuses_file_replaced_after_plan_creation`
  replaces the file after plan creation (same path and bytes, new identity) and proves
  quarantine and permanent execution both leave it untouched. Covered by fixture; the
  built-app step was not re-run.
- Item 2: kept as the intended contract. `storage_repeat_undo_is_idempotent_and_never_mutates_again`
  proves a repeated undo reports `Restored` without touching the restored file or newer
  data later written at that path.
- Item 3: fixed. Selection rejections from a live snapshot now map to `invalid_evidence`;
  `snapshot_unavailable` is reserved for a missing snapshot. Pinned in
  `duplicate_ipc_groups_members_hardlinks_and_subset_plan`. Built app not re-run.

## Harness corrections made during this exercise

Three aborted runs were caused by the driver, not the app, and are recorded so
the failures are not mistaken for product defects:

- The driver hoarded four root authorizations before scanning. The app permits
  only a small number of *unused* authorizations and consumes one per scan
  (`LargeFilesPage.tsx:37`: "Folder authorizations are single-use"). Rewritten to
  pick → scan → next, matching the real UI.
- A step failure aborted the whole session, discarding a person's completed
  dialog work. Failures are now recorded and the run continues.
- Steps were unnamed, so failures could not be attributed. Every step is named.

During diagnosis a change to `MAX_COMPLETED_SNAPSHOTS`/authorized-root bounding
was briefly made under the mistaken belief that the refusal was a product bug.
It was **reverted in full** once the single-use contract was found; the binary
above was rebuilt from the reverted tree, and `cargo test -p windows-platform
--lib storage::` passed (84 tests) after the revert. No product code was changed
by this verification task.
